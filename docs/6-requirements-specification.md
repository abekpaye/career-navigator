# 6 Requirements Specification

The proposed intelligent platform for personalized career navigation and professional development planning will help students and early-career users connect their profiles with documented IT role requirements and create a personal development roadmap. This specification defines the required system behaviour, quality requirements, priorities and acceptance criteria for the integrated application.

| ID | Functional requirement | Priority | Acceptance criteria |
| --- | --- | --- | --- |
| F-01 | The system shall allow users to register, sign in and sign out of a personal account. | Must | Users can register with valid credentials, sign in and sign out. Duplicate registration and invalid credentials are rejected; signing in again restores the saved workspace. |
| F-02 | The system shall support manual creation and editing of a structured profile without requiring a CV or commercial work experience. | Must | Users can add, edit and remove skills, languages, projects and experience, and edit education and interests. A profile can be saved and analysed without a CV, project or work experience. |
| F-03 | The system shall extract profile information from PDF and DOCX CVs and handle unsuccessful uploads. | Must | Readable, text-based PDF and DOCX CVs produce an editable draft based on detected information. Unreadable or unsupported files show an error and allow retry or manual entry; saved data remains unchanged. |
| F-04 | The system shall require user review before analysing newly entered or extracted profile information. | Must | Users can review and correct entered or extracted information before analysis. Recommendations use the saved, reviewed profile; technical skills remain self-reported. |
| F-05 | The system shall normalise skill names and map supported skills to documented ESCO identifiers. | Must | Known aliases resolve to the same skill, and supported skills have documented ESCO mappings. Uncertain mappings are available for review; unmapped terms remain visible. |
| F-06 | The system shall provide a documented catalogue of ten IT professions and their requirements. | Must | The catalogue contains the ten professions defined in the Project Proposal. Each role has a description, level, stack, documented requirements, weights and source references; author-defined assumptions are labelled. |
| F-07 | The system shall provide up to ten ranked, explainable career recommendations using semantic skill mapping and weighted matching rules. | Must | Up to ten roles with matched requirements are ranked by weighted coverage of documented required criteria. Each result explains matched requirements, known gaps and unknown information; unknown criteria receive no matched weight, and the score is labelled as requirement coverage. |
| F-08 | The system shall handle incomplete profiles and insufficient information for assessment. | Must | Profiles with limited relevant information can receive preliminary results. When assessment information is insufficient, the system explains this and offers profile editing or catalogue browsing without displaying a personal percentage. |
| F-09 | The system shall allow users to choose a target profession independently of recommendations. | Must | Users can choose any catalogue profession, including one with low or zero coverage. A plan created without sufficient profile information is labelled general and states its assumptions. |
| F-10 | The system should allow users to compare two professions. | Should | Users can compare two professions and their profile-based results using the same analysed profile. Comparison preserves the selected target. |
| F-11 | The system shall support explicit recommendation updates after saved profile changes. | Must | Saved profile changes mark existing recommendations as outdated. Users can explicitly refresh them; a failed update preserves previous results and their outdated status. |
| F-12 | The system shall generate a personal roadmap for the selected profession and order its steps using documented prerequisites. | Must | The roadmap addresses uncovered role requirements and includes relevant practical, language and career-preparation activities. Prerequisites appear before dependent steps unless already covered by the profile; unknown requirements are identified as planning assumptions. |
| F-13 | The system shall provide actionable information for every required roadmap step. | Must | Each required step states its purpose, suggested actions, expected output, completion criterion, estimated effort and relevant prerequisites. Users can identify what they need to do and when the step is complete. |
| F-14 | The system shall provide reviewed learning resources and use retrieved sources for LLM-written explanations. | Must | Each required step includes a reviewed learning resource, and generated explanations reference retrieved sources. The LLM does not change required steps or scoring rules; unsuccessful generation uses reviewed content or reports failure. |
| F-15 | The system shall let users set and change their available weekly study time. | Must | Users can set a positive number of weekly study hours. Changing this value updates the estimated remaining duration while preserving roadmap tasks and progress. |
| F-16 | The system shall track roadmap progress separately from profile skills and career coverage. | Must | Users can update step status and undo completion; overall progress reflects completed required steps. These actions do not automatically change profile skills, language levels or career coverage. |
| F-17 | The system shall preserve earlier plans when users change the target or regenerate roadmap content. | Must | Creating a replacement plan preserves the previous plan and its recorded progress. Unchanged tasks retain their completion status in the new plan. |
| F-18 | The system shall persist profiles, recommendation results, plans and progress through the backend API and database. | Must | Saved profiles, results, plans and progress remain available after reload, server restart and a new authenticated session. Reopening a plan loads its saved content; failed saves are clearly reported. |
| F-19 | The system should protect unfinished profile edits during navigation. | Should | Users leaving unsaved profile edits can keep editing or discard changes. Draft information is excluded from analysis until reviewed and saved. |

| ID | Non-functional requirement | Priority | Acceptance criteria |
| --- | --- | --- | --- |
| NF-01 | The system shall protect credentials and isolate each user's private records. | Must | Unauthenticated users and other accounts cannot access private records. Passwords are securely hashed, secrets remain server-side, and the deployed application uses HTTPS. |
| NF-02 | The system shall minimise disclosure and retention of CV and profile information during AI processing. | Must | Users are informed about CV processing and external data sharing before upload. AI requests exclude unnecessary personal data; temporary CV files are removed after processing, and private content is excluded from logs. |
| NF-03 | The system shall preserve data consistency during saves and plan replacement. | Must | Interrupted saves or plan replacement do not leave partial records or lose the previous plan. Repeated save requests do not create duplicate records. |
| NF-04 | The system shall produce reproducible scores and roadmap structure from recorded inputs and rules. | Must | The same saved profile, catalogue, mappings and rule versions produce the same scores and required roadmap structure. LLM wording does not affect these results. |
| NF-05 | The system shall remain usable when external AI services fail or time out. | Must | Manual profile entry, catalogue browsing and saved plans remain available during AI service failures. Failed operations show a clear error and a retry or fallback option while preserving saved results. |
| NF-06 | The system shall meet defined response-time targets for the diploma workload. | Must | The proposed target is a response within 2 seconds for at least 95% of ordinary profile and plan API reads and saves under the evaluation conditions in Section 9. Longer operations show loading feedback and finish with a result or a clear error. |
| NF-07 | The system shall provide a responsive interface across the target browsers and screen sizes. | Must | The core workflow works in the desktop and mobile browsers selected for evaluation. At the tested mobile and desktop widths, content remains readable and essential controls are accessible without overlap or clipping. |
| NF-08 | The system shall provide English, Russian and Kazakh interfaces. | Must | The core interface is available in English, Russian and Kazakh. Switching languages preserves profile data, the selected target and progress. |
| NF-09 | The system shall support accessible interaction and clear feedback throughout the core workflow. | Must | The core workflow supports keyboard navigation, labelled inputs and visible focus. Errors identify the affected field, and statuses remain understandable without relying only on colour. |
